# SFEN 설계 결정

아래 항목은 확정된 방향과 현재 구현 상태를 구분해 기록한다.

## 인증 식별자

- 결정: 사용자가 입력한 학번을 내부 가상 이메일로 변환해 Supabase Auth의 인증 식별자로 사용한다.
- 상태: B0-B에서 공통 변환 형식을 `{학번}@students.sfen.invalid`로 구현했다. 학생 계정 생성은 관리자 인증을 요구하는 서버 Edge Function으로 제한하며, 실제 로그인 UI는 B2 범위다.

## 비밀번호 관리

- 결정: 비밀번호는 Supabase Auth에서 관리하며 애플리케이션 테이블에 해시나 원문을 저장하지 않는다.
- 상태: `app_users`에는 비밀번호 필드가 없으며 B0-B 로그인 기반과 서버 계정 생성은 Supabase Auth에 비밀번호를 전달한다. 비밀번호 변경 업무는 B2 범위다.

## 이용 자격과 정지 상태

- 결정: 이용 가능 여부를 나타내는 Boolean `eligibility_status`와 제재 상태인 `suspension_type`을 분리한다. 영구 정지는 `suspension_type = permanent`로 표현한다.
- 상태: B0-A DB Schema에 두 필드와 정지 유형 제약이 반영되어 있다. 자격·정지 변경 업무 로직은 아직 구현되지 않았다.

## 관리자 확률 시연 모드

- 결정: 확률 기반 동작을 시연하는 모드는 관리자 전용으로 제공한다.
- 상태: B0-C에서 확률 판정과 관리자·DB 설정·서버 환경의 3중 Gate를 구현했다. 관리자 시연 화면과 확률을 사용하는 실제 업무 RPC는 아직 구현하지 않았다.

## Lovable 독립 재현

- 결정: Codex에서 구현을 완료한 뒤, 확정된 최종 프롬프트만 새 Lovable 프로젝트에 순서대로 입력해 기능을 독립 재현할 수 있어야 한다.
- 상태: 프로젝트 재현 원칙이다. 최종 프롬프트 세트와 독립 재현 결과가 확정되기 전에는 재현 완료로 간주하지 않는다. 중간 Build/Fix 프롬프트는 최종 세트에 포함하지 않는다.
