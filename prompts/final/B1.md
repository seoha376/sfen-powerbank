# B1 — Station Management, Battery Registration, and Relocation

상태: **Candidate — Lovable 독립 재현 미검증**

선행 조건: `B0.md`의 Core Foundation, Auth, RLS, Battery 상태·시간 규칙 구현 완료

## Final Prompt Candidate

Shared Power Bank Circular Inventory Management System의 B1 관리자 재고 기반을 구현해 주세요. 기존 B0 Schema, Auth/RLS, Battery 상태 전이, 충전 Clock과 테스트를 재사용하고 중복 테이블을 만들지 마세요. B2 회원관리와 B3 이후 대여·반납·충전·수리 업무는 구현하지 마세요.

### Station 관리

- 관리자가 `station_name`, `location`, 음수가 아닌 정수 `slot_capacity`로 Station을 등록하고 전체 목록·상세를 조회하며 정보를 수정할 수 있게 합니다.
- Station별 `available_count`, `occupied_slot_count`, `remaining_slot_count`를 Battery에서 실시간 계산합니다. 별도 Inventory 테이블이나 저장 점유량 컬럼을 만들지 마세요.
- 슬롯 점유 상태는 `Charging`, `Available`, `UnderRepair`뿐입니다. Available 재고와 점유량은 별도 값입니다.
- 용량 수정은 Station 행을 `FOR UPDATE`로 잠근 후 점유량을 다시 계산하고, 현재 점유량보다 작은 값은 거부합니다.
- 인증 사용자의 직접 Station `INSERT`/`UPDATE`를 허용하지 말고 관리자 전용 DB RPC를 사용하세요.

### Battery 등록

- 관리자가 다음 값을 입력합니다: 고유한 UUID `battery_id`, 필수 `model_name`, 양의 정수 `capacity`(mAh), 1 이상의 정수 `cycle_life`, 존재하는 `station_id`.
- 등록 시 `status = Charging`, `current_charge = 0`, `used_count = 0`, `charge_started_at = 등록 시각`, `disposal_confirmed_at = NULL`로 설정합니다.
- B0-C 충전 Clock의 누적값은 0으로 시작하고 기준 시각은 등록 시각, 배율은 현재 System Setting을 사용합니다.
- 목적지 Station을 잠그고 기존 공통 수용량 검사에 점유량 증가 1을 적용합니다. 빈 슬롯이 없으면 전체 작업을 거부합니다.
- Battery INSERT와 최초 `battery_status_history` INSERT를 하나의 PostgreSQL Transaction/RPC에서 처리합니다.
- 최초 History는 `from_status = NULL`, `to_status = Charging`, 관리자 `changed_by`, 등록 Station, 동일한 등록 시각을 사용합니다.
- 중복 ID, 잘못된 수치, 없는 Station, 권한 부족은 명확한 DB 오류로 반환하고 부분 데이터가 남지 않아야 합니다.

### Battery 재배치

- 재배치는 `Charging`, `Available`, `UnderRepair` Battery만 허용합니다. `Rented`, `Overdue`, `Lost`, `Disposed`는 거부합니다.
- 요청에는 Battery ID, 실제 출발 Station ID, 도착 Station ID가 포함됩니다. 출발과 도착은 달라야 하며 Battery가 요청한 출발 Station에 실제로 있어야 합니다.
- Battery 행을 `FOR UPDATE`로 잠근 뒤 출발·도착 Station을 UUID의 안정적인 순서로 잠가 교착 위험을 줄입니다. 도착 Station에는 공통 수용량 검사와 점유량 증가 1을 적용합니다.
- 하나의 DB Transaction에서 `battery.station_id`만 변경하고 History를 기록합니다. 실패 시 모두 rollback합니다.
- History는 현재 상태를 `from_status`와 `to_status`에 동일하게 기록하고, 도착 Station, 관리자 `changed_by`, `reason = Relocation`을 사용합니다.
- 재배치 전후 상태, 충전량, 사용 횟수와 충전 Clock을 변경하지 마세요. 특히 Charging Battery의 `charge_started_at`과 충전 기준 시각을 초기화하지 마세요.
- 인증 사용자의 직접 Battery `INSERT`/`UPDATE`를 허용하지 말고 관리자 전용 DB RPC만 사용하세요.

### 권한과 DB 함수

- 모든 쓰기 RPC는 브라우저 판단과 별도로 `auth.uid()`와 `app_users.auth_user_id`를 연결해 관리자 역할을 DB에서 확인합니다.
- 내부 `SECURITY DEFINER` 함수는 비공개 Schema, 빈 `search_path`, 최소 실행 권한을 사용합니다. Service Role Key를 브라우저에 노출하지 마세요.
- Station 목록과 관리자 Battery 목록에는 필요한 필드만 반환하는 조회 계약을 제공하세요.
- 등록·재배치·용량 수정은 같은 Station 잠금/수용량 함수를 재사용하여 동시 요청에서도 점유량이 `slot_capacity`를 넘지 않게 합니다.

### 관리자 UI

- 기존 React, Tailwind CSS, shadcn/ui 스타일로 하나의 관리자 재고 화면을 구성합니다.
- Station 목록·등록·수정, 현재 점유/전체/남은 슬롯과 Available 수량을 표시합니다.
- Battery 등록 폼, 등록 가능한 Station 선택, Battery 목록과 현재 상태를 제공합니다.
- 재배치 화면은 출발 Station을 선택하면 해당 Station의 재배치 가능한 Battery만 선택하게 하고, 도착 Station은 빈 슬롯이 있으며 출발지와 다른 Station만 제시합니다.
- Station 선택지는 점유량 기준으로 정렬하고 가득 찬 목적지는 선택할 수 없게 합니다.
- 성공 메시지와 필수 입력, 숫자, 중복 ID, 권한, 없는 Station, 동일 Station, 상태, 수용량 오류를 표시합니다.
- 기존 Supabase Auth 세션이 없거나 관리자가 아니면 관리 기능을 표시하지 않습니다. 별도 로그인 우회나 B2 화면을 만들지 마세요.

### 기능 검증 기준

- Station 등록·수정, 점유량 계산, 용량 축소 거부와 일반 사용자 쓰기 거부를 검증합니다.
- Battery 정상 등록의 모든 초기값과 최초 History, 중복 ID·수치·Station·수용량 오류, 실패 시 rollback을 pgTAP으로 검증합니다.
- 허용 상태 재배치, 금지 상태, 동일 Station, 잘못된 출발지, 목적지 수용량, History, 상태·충전 Clock 보존을 검증합니다.
- 일반 사용자의 등록·재배치 거부, 직접 테이블 쓰기 차단, Station 행 잠금과 안정적인 잠금 순서가 동시 수용량 초과를 방지하는 계약을 검증합니다.
- UI 테스트는 관리자 접근, 입력 검증, 등록, 재배치 필터, 성공·실패 안내를 검증하고 실제 DB 통합 테스트와 구분합니다.
