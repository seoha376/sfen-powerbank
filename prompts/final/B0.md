# B0 — Core Foundation, Auth, Security, and Shared Logic

상태: **Candidate — Lovable 독립 재현 미검증**

선행 조건: 새 Lovable 프로젝트, Supabase 연결, React + Vite + TypeScript

## Final Prompt Candidate

Shared Power Bank Circular Inventory Management System의 B0 공통 기반을 구현해 주세요.

### 기술과 범위

- React + Vite + TypeScript, Tailwind CSS, shadcn/ui, Supabase JavaScript Client를 사용합니다.
- Vitest 기반 TypeScript 테스트와 Supabase Migration/pgTAP 구조를 구성합니다.
- 실행 가능한 최소 App Shell만 만들고 회원가입·승인·대여·반납·관리자 업무 화면은 만들지 않습니다.
- 실제 비밀키, 비밀번호, 학생 개인정보를 저장소에 기록하지 않습니다.
- 공개 Auth 회원가입은 비활성화하고 비밀번호 최소 길이는 8자로 설정합니다.

### PostgreSQL Schema

다음 6개 public 테이블을 Migration으로 만드세요.

1. `app_users`
   - `user_id` text PK, `auth_user_id` nullable UUID UNIQUE FK to `auth.users.id` (`ON DELETE SET NULL`), `user_name`
   - `role`: `user | administrator`
   - `user_status`: `Enrolled | Graduated | NULL`
   - `approval_status`: `Pending | Approved | Rejected | NULL`
   - `eligibility_status` boolean default false
   - `suspension_type`: `none | temporary | permanent`, `suspended_until`, `graduation_year`, `certificate_file`
   - 일반 사용자 ID는 정확히 8자리 숫자이며 관리자는 별도 ID를 허용합니다. 비밀번호 필드는 만들지 않습니다.
2. `stations`
   - UUID PK, `station_name`, `location`, `slot_capacity >= 0`
3. `batteries`
   - UUID PK, `model_name`, `capacity > 0`, `cycle_life >= 1`, `used_count >= 0`
   - `status`, nullable station FK, `current_charge` 0~100, `charge_started_at`, `disposal_confirmed_at`
   - B0-C Clock: `charge_simulation_elapsed_seconds >= 0`, nullable `charge_time_anchor_at`, `charge_time_scale > 0`
4. `rentals`
   - UUID PK, user/battery/rental station FK, `rental_time`, nullable return station/return time
   - `penalty_type`, `compensation_multiplier`은 0/1/3, `compensation_confirmed_at`
   - `return_time >= rental_time`
   - B0-C Clock: `simulation_elapsed_seconds >= 0`, `simulation_anchor_at`, `simulation_time_scale > 0`
5. `battery_status_history`
   - UUID PK, battery FK, nullable `from_status`, `to_status`, `changed_at`, changed user/station/reason/rental FK
   - 최초 등록만 `from_status = NULL`, `to_status = Charging`을 허용합니다.
6. `system_settings`
   - `settings_id = 1`인 단일 행
   - 기본값: `rental_period_days = 7`, `long_term_days = 60`, `time_scale = 1`, `battery_unit_price = 30000`, `demo_mode_enabled = false`
   - 값은 양수이고 `long_term_days > rental_period_days`입니다.

### Battery 공통 규칙

상태는 `Charging`, `Available`, `Rented`, `Overdue`, `Lost`, `UnderRepair`, `Disposed`입니다.

- 최초 등록 → Charging
- Charging → Available / UnderRepair / Disposed
- Available → Rented
- Rented → Charging / Overdue / Lost
- Overdue → Charging / Lost / Disposed
- Lost → Disposed
- UnderRepair → Charging / Disposed
- Disposed는 종료 상태입니다.
- 같은 상태 재배치는 Charging/Available/UnderRepair에서만 명시적 relocation으로 허용합니다.
- 대여 가능 상태는 Available뿐입니다.
- Station 슬롯은 Charging/Available/UnderRepair만 점유합니다.
- Available 재고는 Battery에서 계산합니다.
- 활성 Rental은 `return_time IS NULL`이고 Battery가 Rented 또는 Overdue인 경우입니다.

### Auth와 서버 계정 생성

- 8자리 학번을 `{학번}@students.sfen.invalid` 내부 이메일로 바꾸는 단일 공통 함수를 만드세요.
- 로그인 공통 함수는 내부 이메일과 비밀번호를 Supabase Auth에 전달합니다.
- 학생 Auth 계정 생성과 email confirmation은 관리자 JWT를 검증하는 서버 Edge Function에서만 수행합니다.
- Edge Function은 관리자 역할을 `app_users`에서 확인하고, 프로필 연결 실패 시 생성한 Auth 사용자를 정리해야 합니다.
- 환경 변수 기반 관리자 초기화 스크립트를 제공하세요. Secret/Service Role key는 서버에서만 사용하고, 반복 실행 시 기존의 신뢰 가능한 Auth metadata와 프로필을 확인해 중복 생성하지 마세요.

### RLS와 Storage

- 6개 업무 테이블 모두 RLS를 활성화합니다.
- 일반 사용자는 자신의 `app_users`와 `rentals`만 조회하고 역할·승인·자격이나 Battery/Rental/History를 임의 변경할 수 없습니다.
- 관리자 여부는 `auth.uid()`와 `app_users.auth_user_id` 연결로 DB에서 판정합니다. 사용자 수정 가능한 metadata를 권한 근거로 사용하지 않습니다.
- 관리자만 업무 테이블을 변경하고 Battery History를 조회합니다.
- Station별 Available 수량과 슬롯 점유 수량만 반환하는 제한된 `station_inventory` 보안 호출자 View를 제공하세요.
- `SECURITY DEFINER` helper는 비공개 Schema, 빈 `search_path`, 최소 실행 권한을 사용합니다.
- `enrollment-certificates` Private Bucket을 만들고 PDF/JPEG/PNG, 최대 5 MiB로 제한합니다.
- Storage 객체의 첫 경로는 Auth UUID이며 본인 소유 경로와 관리자만 접근할 수 있어야 합니다.

### 시간과 충전

- 실제 경과시간, 시뮬레이션 경과시간, 대여 일수, 연체 일수를 계산하는 순수 TypeScript 함수를 만드세요. 현재 시각을 주입할 수 있어야 합니다.
- 정확히 7일은 Overdue가 아니고 7일 초과부터 Overdue입니다. 정확히 60일은 장기 미반납이 아니고 60일 초과부터 해당합니다.
- 충전은 시뮬레이션 1분당 10%p이며 DB 정수 필드에 맞춰 소수 %p를 내림하고 0~100%로 제한합니다.
- Scheduler를 사용하지 말고 조회/업무 처리 시 계산합니다.
- `time_scale` 변경 시 활성 Rental과 Charging Battery의 기존 구간을 이전 배율로 누적한 뒤 기준 시각과 새 배율을 교체하는 원자적 DB 함수를 만드세요.
- 직접 `time_scale`을 변경해 과거 시간이 소급 계산되지 않도록 보호하세요. 관리자이며 DB demo mode가 활성화된 경우만 변경할 수 있어야 합니다.

### 확률과 시연 Gate

- 사용 중 고장 5%, 충전 중 고장 3%, 수리 성공 90%, 수리 실패 10%를 공통 함수로 구현합니다.
- 테스트용 고정 난수 공급자를 주입할 수 있고 기본값은 실제 난수입니다.
- 강제 결과는 관리자, `demo_mode_enabled`, 서버 환경 `SFEN_DEMO_MODE_ALLOWED`가 모두 참일 때만 허용합니다.
- 운영 환경 Gate 기본값은 false입니다. 클라이언트가 전달한 역할이나 demo 활성값을 신뢰하지 않습니다.
- 서버 전용 Supabase Client로 `app_users.role`과 `system_settings.demo_mode_enabled`를 직접 조회해 Gate를 구성하는 공통 resolver를 제공하세요.
- 관리자 시연 화면은 만들지 않습니다.

### 후속 Transaction 계약

실제 B1~B6 RPC는 만들지 말고 TypeScript 입력·출력 타입, 공통 오류 코드와 다음 계약만 정의하세요.

- B1: 관리자 권한, Battery/Station `FOR UPDATE`, 등록·재배치·수용량·History 원자 처리
- B3: 자격·승인·정지·활성 대여 검사, User/Battery 잠금, Rental/Battery/History 원자 처리
- B4: Rental/Battery/Station 잠금, 수용량, 반납 필드, 사용 횟수, Charging Clock, History 원자 처리
- B5/B6: Battery/관련 Rental 잠금, 상태 전이·확률 Gate, 충전·수리·연체·분실·폐기와 History 원자 처리
- 상태 변경과 History는 함께 성공하거나 rollback해야 하며 클라이언트의 여러 요청으로 DB Transaction을 대체하지 않습니다.

### 테스트와 환경

- 시간 7일/60일 경계, 배율 체크포인트, 충전 0~100%, 확률 경계·고정 난수, 관리자 시연 3중 Gate, 상태 규칙과 Transaction 계약을 Vitest로 작성하세요.
- Migration 기본값·Clock 체크포인트·관리자 권한은 pgTAP으로 작성하세요.
- 실제 DB가 필요한 검증은 단위 테스트와 구분하세요.
- `.env.example`에는 이름만 기록하세요: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, 서버 전용 Supabase Secret/Service Role key, 관리자 초기화 값, `SFEN_DEMO_MODE_ALLOWED=false`.
- 기존 기능을 넘어 B1~B6 업무 화면이나 업무 RPC를 구현하지 마세요.
